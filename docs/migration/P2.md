## Componentes modificados

- CLI: init-workspace, approve-tool y run-tool con identidad cliente/proyecto, raíz externa y config JSON. Errores controlados; el bootstrap no puede escribir en el checkout. Punteros nuevos relativos.
- storage: rutas canónicas, rechazo de symlinks/hardlinks/archivos especiales, separación por cliente, lock de escritor, UUID de run, escritura atómica y aprobaciones del operador con acción/hash de contenido y política/caducidad/uso único.
- executor: un adaptador experimental python.unittest; ejecución únicamente con Docker local e imagen oficial fijada por digest, sin descarga automática, red, credenciales heredadas ni fallback de shell host. Snapshot filtrado montado solo lectura; resultados/aprobaciones fuera del contenedor. Límites de CPU, memoria, procesos, archivo, tiempo y salida; intento de limpieza acotado por nombre único.
- config: límites explícitos; memoria automática deshabilitada; imagen null impide ejecutar hasta configuración y revisión del operador.
- utils/schemas: JSON atómico, hash de bytes, rechazo de NaN, IDs seguros y presupuestos no negativos. env_hash deja de usar shell.
- context: fuentes explícitas opcionales y snapshots por ciclo sin sobrescritura. Fuentes legadas no se reconstruyen.
- memory/policy/harness: no inicializar memoria de fábrica al leer; strings/booleanos del productor no autorizan operaciones; raíces y rutas comprobadas. Agentes académicos siguen bloqueados.
- Identidad del paquete: versión 0.1.0 centralizada para el runtime; estado experimental, no release aprobado.

## Decisiones tomadas

Docker pertenece al stack aprobado. Bubblewrap se comprobó durante diagnóstico del entorno, pero **no se incorpora como dependencia ni backend de la fábrica**. No se instalan Docker ni daemons/servicios del sistema. La prueba de Bubblewrap no acredita el aislamiento del adaptador Docker.

Se permite crear y revisar el código local sin declararlo aprobado en seguridad. No se habilitan agentes con acceso a procesos ni se ejecutan proyectos no confiables. La aprobación de herramienta procede del operador host; el modelo/brief no puede crearla desde el contenedor. Este control no autentica personas frente a un atacante con la misma cuenta Unix o acceso al daemon Docker.

Referencia técnica consultada: [docker run, documentación oficial](https://docs.docker.com/engine/containers/run/). Se utilizan montaje explícito, restricciones de red/recursos y digest de imagen. Las opciones deben validarse en el host de pruebas real antes de habilitar la capacidad.

## Pruebas ejecutadas

Suite completa antes del cierre documental: 58 passed, 1.32 s, mismo comando de P0. Incluye locks, IDs de runs, atomicidad ante error, traversal, enlaces, cruce de clientes, aprobación cambiada/expirada/reutilizada, memoria desactivada, snapshots inmutables, dry-run, ausencia de Docker, shell no allowlisted, presupuesto, redacción y retorno CLI.

Timeout, límite de salida y cero tests se probaron con procesos host **sintéticos y confiables** para comprobar el lector de resultados. No son tests de aislamiento Docker. Los tests de argumentos del contenedor comprueban configuración, no garantías del kernel. La ejecución real del contenedor no está verificada.

## Errores encontrados

Docker no está instalado/disponible y no hay imagen local aprobada por digest. El ejecutor devuelve not_answerable sin iniciar proceso; no descarga una imagen ni intenta ejecutar tests en host como sustitución.

## Problemas pendientes

Aprobar el modelo de amenaza y configuración. No se soportan aún generadores, escritura de producto por herramientas, reanudación de jobs ni actualización de productos. No se promueve P2 ni se declaran completadas fases dependientes.
