# P3 — Preparación del piloto corporate-site

Fecha: 2026-09-10. Alcance de esta entrega: normalización de directorios, P3.1 y P3.2. P3.3 NO iniciada. No hay plantilla, componentes web ni producto generado.

## Autorización y decisiones

El usuario aprobó P2 como PASS_WITH_LIMITATIONS y aceptó sus límites operativos. Aprobó la incorporación selectiva del prototipo, corporate-site v0.1.0 y el plan P3 v0.1.0. Esta entrega tiene autorización únicamente para congelar entradas y contratos; la siguiente etapa requiere revisión humana.

Se aprueba una landing en /, fiel a la composición actual disponible, con React/TypeScript/CSS Modules. Header, hero, dominios dentro del hero, presentación, planes de ejemplo, servicios, FAQ, contacto, footer, chat y resumen «Tu consulta». No se trasladan ventas.html/desarrollo-web.html como rutas; son referencias editoriales. Se excluyen testimonios, presencia territorial y garantías no aprobadas. Tampoco hay autenticación, BD, administración ni despliegue.

Dominios: formato local y «disponibilidad no consultada». Chat: respuestas locales explícitamente demostrativas. «Tu consulta»: interés, sin pedidos/pagos. Contacto: preparación/copia, explícitamente no enviado. Estado en memoria; sin WHOIS, Gemini, WHMCS, pagos ni servicios externos. Precios específicos del piloto son provisionales/configurables, nunca defaults comerciales del motor.

## P3.1 — Entradas congeladas

Se renombraron las carpetas hermanas a nexonova-factory y nexonova-prototype, sin copiar ni transformar archivos del prototipo. Se verificaron los 99 hashes antes/después. El manifiesto completo contiene SHA-256, tamaño y clasificación por cada archivo, incluidos binarios y documentación. La fuente no contiene dependencias/builds ni archivos de secretos detectados por nombre en este snapshot. Una futura adición de .env o enlaces requiere revisión: el verificador bloquea sin incorporarlos.

Archivos: [manifiesto NexoNova](../../config/pilots/nexonova/source-manifest.json), [registro de fuentes](../../config/sources.json), [renombrado](RENAME_VALIDATION.json).

El snapshot es una referencia versionada por contenido al árbol preservado, no un backup ni un bloqueo físico contra ediciones del equipo. Una modificación, archivo añadido/retirado o enlace rompe verify_source. No se fija una ruta absoluta: el registro de operador autoriza ../nexonova-prototype relativo al checkout. No se transfiere esa ruta al producto.

Selección: HTML como referencia para REBUILD; CSS visual para ADAPT; funciones de formato de dominio de storefront para ADAPT; instrucciones/documentación como evidencia KEEP. APIs externas, middleware estático, configuración Vercel y GSAP sin consumidor quedan DROP para el futuro producto, sin borrar sus originales. Assets sin evidencia suficiente siguen REVIEW. Los targets son destinos propuestos, no archivos creados.

Se registran cinco recursos ausentes: service-values.css, web-development.css, promo-cocker.jpg, rocket-editorial-v3.png y contact-specialist-v1.png (rutas completas en manifiesto). No se inventaron ni sustituyeron. Se mantienen pendientes selección/procedencia de imágenes/logos/iconos, distribución local y licencia de Inter, decisión sobre recursos ausentes y textos comerciales definitivos.

## P3.2 — Contratos

[factory/product_contracts.py](../../factory/product_contracts.py) reutiliza validate_strict sin alterar WORK_ORDER_SCHEMA P2. Exportaciones en schemas/: product-work-order.v1, corporate-site.v0.1.0 y source-manifest.v1.

WorkOrder de producto: prepare-project, identidad cliente/proyecto, hashes de especificación/manifiesto, autorización contextual del usuario y límites de inspección. Solo permite snapshot/validate-contracts; generation=not-authorized. Es deliberadamente distinto de una orden P2 de test. No es una aprobación criptográfica ni concede permisos al código del prototipo.

Especificación: marca/tokens, secciones, planes provisionales, servicios, modos locales, assets candidatos y criterios de aceptación. No se generaron textos definitivos ni se completaron decisiones editoriales por inferencia. La segunda configuración sintética tiene identidad/configuración independientes y una fuente ficticia local; todavía no demuestra dos sitios generados (eso corresponde a P3 posterior).

Manifiesto: hashes originales separados de decisiones/targets. tree_hash vincula contenido; manifest_hash vincula también selección y aprobaciones. Si cambia especificación/selección, la orden anterior se rechaza. Registro de fuentes privado al operador con raíz relativa y hash esperado.

Validaciones: versiones y campos estrictos, tipos, rutas canónicas, duplicados, integridad, presupuesto, identidad/scope, referencias de assets y coherencia de aprobación. Los JSON schemas describen estructura; la validación semántica en Python es obligatoria. Un JSON estructuralmente válido no basta para aceptar un producto.

El gate require_material_ready es independiente: las entradas pueden ser válidas para preparación mientras material pendiente impide generación. El comando --require-ready devuelve código 2 para el piloto actual; es el comportamiento esperado, no un fallo de tests. Aun al resolver material, la orden actual no autoriza generar.
